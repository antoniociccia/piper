# PIPER demo host

A self-contained Linux container that looks and behaves like a small generic
production server. Built so you can drop PIPER in front of it, ask diagnostic
questions, and record a demo where the agent *actually finds things*.

The host runs a real `sshd` (key-auth only, hardened config), comes with
realistic logs, a familiar `/opt/<app>` layout, and a couple of long-running
"fake" processes so `ps` looks plausible. Three anomalies are planted on
purpose so PIPER's read-only flow has something to report.

> This is not the e2e test fixture at `tests/fixtures/sshd-docker/`. That one
> is minimal and tuned for fast, deterministic CI. *This* one is for show.

## What's inside

| Path                                       | Purpose                                       |
|--------------------------------------------|-----------------------------------------------|
| `Dockerfile`                               | Debian 12 base, sshd + realistic CLI toolset (curl, htop, lsof, jq, sysstat, …) |
| `docker-compose.yml`                       | Single service `demo-host`, exposes `2222 → 22` |
| `keys/piper-demo[.pub]`                    | User keypair (generated by `setup.sh`, gitignored) |
| `host-keys/ssh_host_*`                     | Pinned host keys (stable fingerprint across rebuilds) |
| `fakefs/etc/motd`                          | PIPER demo banner shown on login              |
| `fakefs/opt/orderly/`                      | "App" install: `config.yml`, `.env.example`   |
| `fakefs/var/log/orderly/app.log`           | App log with the planted cache-down error     |
| `fakefs/var/log/orderly/worker.log`        | Stale worker log proving the worker crashed at boot |
| `fakefs/var/log/nginx/access.log`          | Access log with the planted scanner traffic   |
| `fakefs/usr/local/sbin/demo-entrypoint.sh` | Spawns fake `node` + `nginx` processes, then sshd |
| `setup.sh`                                 | Bring the demo up (idempotent)                |
| `teardown.sh`                              | Bring it down. `--wipe` also removes generated keys |

### "Fake" processes

`demo-entrypoint.sh` uses bash's `exec -a NAME COMMAND` trick to launch
`sleep infinity` under cosmetic names:

- `node /opt/orderly/dist/server.js`  — the web component
- `nginx: worker process`             — the reverse proxy

Both show up in `ps aux | grep -E 'orderly|nginx'` exactly the way the real
binaries would. **Notably absent**: the `orderly worker` process. The on-disk
config declares it enabled (`/opt/orderly/config.yml`), the log file confirms
it briefly booted then died (`/var/log/orderly/worker.log`), and `ps` confirms
it's not currently running. That's anomaly #3.

## Quickstart

```bash
# 1. Make the scripts executable (one-time)
chmod +x demo/setup.sh demo/teardown.sh

# 2. Bring the demo host up
bash demo/setup.sh

# 3. (Optional) sanity check the SSH connection
ssh -i demo/keys/piper-demo \
    -o UserKnownHostsFile=/dev/null \
    -o StrictHostKeyChecking=accept-new \
    -p 2222 deploy@127.0.0.1 \
    "cat /etc/motd && ps aux | grep -E 'orderly|nginx' | grep -v grep"

# 4. Wire it into PIPER
#    (inside PIPER's TUI, or via CLI)
/env add demo deploy@localhost:2222 --key demo/keys/piper-demo

# 5. Tear down when finished
bash demo/teardown.sh           # keep keys (next setup is instant)
bash demo/teardown.sh --wipe    # also delete keys (back to factory state)
```

## Planted anomalies

The demo's whole point is that PIPER *finds* these without help.

### 1. Cache (redis) is down

Every minute or so the app log emits a clear, parseable `ECONNREFUSED` on
`127.0.0.1:6379`:

```
ERROR [cache] connect ECONNREFUSED 127.0.0.1:6379
WARN  [cache] running in degraded mode (no cache); responses will be slower
```

There is no redis process running on the host. The app survives because the
caller path explicitly falls back to "DB cache miss" mode — but every request
is now hitting Postgres directly. PIPER should: notice the recurring error,
verify nothing is listening on `:6379` (e.g. via `ss -ltnp` or `lsof -i :6379`),
and report *"cache is unreachable, the app is in degraded mode, request
latency in the log is now ~190 ms vs the cached path."*

### 2. Vulnerability scanner traffic

`/var/log/nginx/access.log` mixes normal traffic with bursts from
`198.51.100.42` running user-agent `Example-Audit-Bot/1.0`, probing:

- `/v1/.env`, `/.env`, `/api/.env`, `/v1/.env.production`, `/v1/.env.local`
- `/var/task/.env`, `/var/task/index.js`, `/var/task/handler.py`, `/var/task/config.json`, `/var/task/secrets.json`
- `/v2/keys`, `/v2/secrets`, `/v2/users`, `/v2/admin`, `/v2/internal`, `/v2/debug`
- `/.aws/credentials`, `/.git/config`, `/.git/HEAD`
- `/actuator/env`, `/actuator/heapdump`

All return 404. The signal is the *pattern*, not the response code. PIPER
should single out the IP + UA combination and call it "automated
reconnaissance, not human traffic."

### 3. The worker is declared enabled but is not running

`/opt/orderly/config.yml` declares three components: `web` (enabled), `worker`
(enabled), `scheduler` (disabled). `ps aux` on the host shows the web
process — but not the worker. Cross-referencing with
`/var/log/orderly/worker.log` shows why:

```
FATAL [worker] cache is required for job processing; refusing to start in degraded mode
INFO  [worker] exiting with code 1
```

So anomalies #1 and #3 are causally linked: redis is down → worker refused
to start → background jobs are silently piling up. PIPER should connect the
dots, not just list them separately.

## Demo recording — prompt cookbook

These are the prompts that exercise the fixture nicely, ordered from broad to
specific. Use them in this order for the best storytelling.

1. **Broad situational read**
   `analizza demo`
   *— forces a grounded health report. PIPER tails logs, runs `ps`, `ss`,
   reads the app config. The cache-down error + missing worker + scanner
   traffic should all surface.*

2. **Drill into the loudest signal**
   `controlla i log di orderly su demo`
   *— PIPER zooms into `/var/log/orderly/app.log`, identifies the recurring
   `ECONNREFUSED` on `:6379`, and verifies nothing is listening on that port.*

3. **The "huh, that's weird" moment**
   `il config dichiara un worker, ma è in esecuzione?`
   *— PIPER diffs `/opt/orderly/config.yml` (worker enabled) against
   `ps aux` (no worker process) and links it to the FATAL line in
   `worker.log`.*

4. **Security flavor**
   `qualcuno sta scansionando il sito di demo?`
   *— PIPER aggregates by IP + user-agent in `/var/log/nginx/access.log`
   and surfaces `198.51.100.42 / Example-Audit-Bot/1.0` probing for
   `.env` / `var/task` / `v2/*` endpoints.*

5. **(Bonus) ask for the safe next step**
   `che fix mi proponi? non eseguire niente`
   *— PIPER stays read-only and proposes a `mutate` action (start redis, then
   restart the worker), shows the dry-run, waits for approval. Sells the
   gate visually.*

## Notes

- The container hostname is `app-host-01` — picked so logs and prompts reference
  a name that looks production-ish without naming any real product.
- The user is `deploy`, key-auth only, with **passwordless sudo** (NOPASSWD).
  The docker shim refuses non-root callers — exactly like a real Docker
  socket — so PIPER's reactive-sudo flow has a realistic boundary to hit and
  `sudo -n` is the way through it. Sshd is hardened: no passwords, no root
  login, no agent forwarding.
- All ports outside `2222` stay closed. The demo host does not phone home.
- Generated keys live under `demo/keys/` and `demo/host-keys/` and are
  gitignored. They survive `teardown.sh` (so the next `setup.sh` is fast) and
  only get wiped with `--wipe`.
- The demo also relies on plain Linux signals: `ps`, `ss`, `lsof`, `tail`,
  `cat`, `grep` — all the obvious ones a remote SRE would reach for.

## The `piper-docker-shim`

To exercise PIPER's `docker.*` actions against the demo host without bringing
up a real Docker daemon inside the container, we ship a tiny shell script at
`fakefs/usr/local/bin/piper-docker-shim`. It hardcodes the output of `docker
ps / logs / inspect / compose ps|up|restart|down` for the four planted demo
containers. A symlink at `/usr/local/bin/docker` resolves PIPER's
`docker ps …` argv to the shim.

Two behaviours make the demo realistic:

- **Root gate.** Run as a non-root user, every subcommand fails with the
  classic `permission denied … /var/run/docker.sock` error (exit 1) — which
  is what triggers PIPER's reactive-sudo proposal. Under `sudo` it works.
- **Restart state.** `compose restart` (and `compose up`) drop a marker at
  `/tmp/piper-demo-restarted`; from then on `compose ps` reports every
  service running, so PIPER's verify step sees the stack healthy.
  `scripts/record-demo.sh` clears the marker before each take so recordings
  always start from the broken state (worker + redis exited).

**It is not Docker.** It contains no Docker source code, runs no engine,
manages no containers. It just prints static text in the shape PIPER expects.
